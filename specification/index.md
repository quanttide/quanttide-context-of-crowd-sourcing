# 众包平台定位与领域模型

以真实生产需求为中心来设计。量潮课堂的实践部分本质上是一个生产型众包平台，教学是参与者通过真实工作获得的附加价值，而不是任务存在的首要目的。

这会带来一个重要的定位变化：

> 不是为了让学生练习而设计任务，而是把真实业务拆解成可供参与者承接、执行和交付的任务。学生通过参与这些任务积累实践经验。

## 核心领域模型

| 概念 | 英文 | 定义 |
|---|---|---|
| 项目 | Project | 一项完整的业务需求或生产目标 |
| 任务 | Task | 项目中可以独立执行和验收的工作单元 |
| 认领 | Claim | 参与者承接任务的行为 |
| 提交 | Submission | 参与者提交的工作成果 |
| 验收 | Review | 对工作成果进行审核 |
| 报酬 | Reward | 完成任务后获得的经济或非经济回报 |

## 业务流程

```text
需求方
  │
  ▼
发布项目 Project
  │
  ▼
拆解任务 Task
  │
  ▼
任务公开
  │
  ▼
参与者认领 Claim
  │
  ▼
执行任务
  │
  ▼
提交成果 Submission
  │
  ▼
成果验收 Review
  │
  ▼
支付报酬 Reward
```

## 量潮课堂的特殊价值

量潮课堂可以在普通众包平台的基础上增加三种能力：

- **实践机会**：参与者可以通过真实业务获得工作经验。
- **能力证明**：通过真实任务的交付记录形成能力档案。
- **成长路径**：根据参与者完成的任务，逐步获得更复杂的工作机会。

这样，教学系统与众包系统就形成了互补关系：

- 众包系统负责生产协作。
- 课堂系统负责知识学习和能力成长。

## 命名

先采用以下英文名：

- `Project`：项目
- `Task`：任务
- `Claim`：认领
- `Submission`：交付成果
- `Review`：验收
- `Reward`：报酬

其中，**Task（任务）应该是众包系统最核心的业务对象**，而 Project 是组织和管理任务的上层对象。

## 设计原则

不要把 Task 设计成只能服务于学生的练习题。它应该是一个真正的生产任务，即使没有教学系统，这个任务也有独立存在的业务价值。
